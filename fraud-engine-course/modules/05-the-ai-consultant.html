The AI Consultant — and Why It Is Never Allowed to Decide

How to bolt an AI assistant onto a system that blocks people's money — without ever letting the AI make that call.

The most important question in this whole codebase

Everyone wants to bolt AI onto everything. So here is the question that matters most: how do you add an AI assistant to a system that decides whether to block someone's money — without ever letting the AI make that call?

Think of a car's built-in GPS co-pilot. The GPS suggests a route. But it can never touch the steering wheel or the brakes — you always drive. Even when it says confidently "turn here," the dashboard still shows "driver must confirm." And if the GPS loses signal, the car keeps driving exactly as before.

🚗
The driver = the rule engine

The deterministic rule engine makes the real decision. It is the only thing with hands on the wheel.

📡
The GPS = the AI advisor

A local AI model writes a short note after the decision, only to help a human reviewer. Advice only, never control.

💡
Why you should care

This is the lesson for steering AI: keep the AI a helpful commentator, never the judge, in anything high-stakes. When you build with AI, you will learn to ask: where is the human in the loop, and what happens when the model is wrong or down?

First, a promise: "any advisor must keep this shape"

Before plugging in any AI, the code writes down a contract — an interface. It says: whoever the advisor is, it must answer one question and admit whether it is even real.

CODE 
public interface AdvisoryService {

    AdvisoryResponse adviseOn(Decision decision);

    /** Indicates whether a real advisor (e.g. Ollama) is wired up. */
    default boolean enabled() { return false; }
}
PLAIN ENGLISH

A promise that any AI advisor must keep.

One method: hand it a finished decision, get back commentary. That is its only job.

A second question: "are you a real advisor?"

The default answer is "no." Off by default — you have to actively switch a real one on.

🤝
Why the contract comes first

Because everything talks to this promise — not to "the AI" directly — the rest of the app never has to know whether AI is actually on. Swapping advisors becomes a one-line setting change. Engineers call this the strategy pattern.

One switch: AI OFF vs AI ON

There are two advisors that keep the same promise. A single setting — app.advisory.enabled — decides which one the app loads. Nothing else changes.

🔘

OFF (the default)

Loads the do-nothing stand-in. Asked for advice, it replies "unavailable." The whole app runs perfectly with no AI model installed at all.

🔥

ON

Loads the real Ollama advisor. It calls a local model with a 2-second fuse, returns commentary — but still flags humanReviewRequired = true.

OFF: the safe do-nothing stand-in

CODE 
@Component
@ConditionalOnProperty(prefix = "app.advisory", name = "enabled", havingValue = "false", matchIfMissing = true)
@ConditionalOnMissingBean(value = AdvisoryService.class, ignored = NoopAdvisoryService.class)
public class NoopAdvisoryService implements AdvisoryService {

    @Override
    public AdvisoryResponse adviseOn(Decision decision) {
        return AdvisoryResponse.unavailable();
    }
}
PLAIN ENGLISH

Load this piece into the app...

...but only when the AI setting is "false" — or simply not set at all (that is what matchIfMissing means).

And only if no real advisor already grabbed the spot.

This is the empty stand-in — a null object.

Asked for advice...

...it just replies "unavailable." No AI, no crash, no hole in the system.

What happens when the AI is slow or broken?

When the real advisor is on, it calls a local Ollama model. But a local model can be slow, or down, or send back gibberish. The code refuses to let any of that touch a real decision.

CODE 
        try {
            String response = http.post()
                    .uri("/api/generate")
                    .contentType(MediaType.APPLICATION_JSON)
                    .body(body)
                    .retrieve()
                    .body(String.class);
            return parse(response);
        } catch (RestClientException e) {
            log.warn("advisory: ollama call failed cause={}", e.toString());
            timeoutCounter.increment();
            return AdvisoryResponse.timedOut();
        }
PLAIN ENGLISH

Try to send the question to the local AI and wait for a reply...

...post the request to the model's address...

...with the question packaged up, then read whatever text comes back.

If a real answer arrives, turn it into structured commentary.

But if anything goes wrong — slow, broken, unreachable — do NOT crash.

Quietly note the failure in the logs.

Tick a counter (so a circuit breaker can trip after too many failures).

Return a "timed out" answer. The decision the customer already got is never affected.

⏱️
Graceful degradation

A 2-second timeout plus a circuit breaker mean a slow or broken AI can never delay or break a real decision. The system gets weaker, not dead — engineers call this graceful degradation.

Even a perfect answer still demands a human

Here is the heart of it. When the AI replies cleanly, the code builds a success response — and the very last value is hard-coded to true. That is the human-review-required flag.

CODE 
            okCounter.increment();
            return new AdvisoryResponse(AdvisoryStatus.OK, summary, concerns, confidence, true);
PLAIN ENGLISH

Count this as a successful AI call.

Build the reply: status OK, a summary, any concerns, a confidence score — and that final true is "a human must still review this." Hard-coded true even on a perfect answer. The AI is never allowed to be a green light.

And every failure shape says the same thing. Timed out, unavailable, gibberish — all three carry empty content, zero confidence, and true for "a human must check."

CODE 
    public static AdvisoryResponse timedOut() {
        return new AdvisoryResponse(AdvisoryStatus.TIMED_OUT, null, List.of(), 0.0, true);
    }

    public static AdvisoryResponse unavailable() {
        return new AdvisoryResponse(AdvisoryStatus.UNAVAILABLE, null, List.of(), 0.0, true);
    }

    public static AdvisoryResponse malformed() {
        return new AdvisoryResponse(AdvisoryStatus.MALFORMED, null, List.of(), 0.0, true);
    }
PLAIN ENGLISH

The "timed out" reply: no content, zero confidence...

...and true — a human must review.

The "unavailable" reply (the AI is off or down)...

...same: empty, zero confidence, true.

The "malformed" reply (the AI sent gibberish)...

...also true. No matter how the AI fails, the answer is "don't trust me, get a person."

The most important lesson in this course

In a high-stakes system, the AI advises; it never decides. Make that boundary structural — an off-switch, a timeout, and a human-review flag the model can never set — not just a hopeful instruction in a prompt. The GPS suggests the turn; you still hold the wheel.

Four patterns that keep AI on a leash

None of this is luck. Four well-known engineering patterns combine so the AI structurally cannot become the decider.

🔀

Strategy pattern

One switch swaps the advisor. Off-stand-in or real AI — the rest of the app neither knows nor cares which is loaded.

🚫

Null object

A safe do-nothing stand-in fills the gap when AI is off, so the app never has a hole to crash through.

⚡

Graceful degradation

A timeout plus a circuit breaker mean a slow or broken AI weakens the help, never the decision.

🛡️

Safety flag by policy

"A human must review" is decided by policy, hard-coded into every reply — never by the model.
