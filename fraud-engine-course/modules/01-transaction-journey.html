The Journey of a Transaction

From a tap on a card to a verdict in milliseconds — the exact path your payment takes through a fraud engine.

What is this thing?

This whole course is about one program: a real-time brain that scores bank card payments and instantly says ALLOW, REVIEW, or BLOCK — always with a plain-English reason attached.

Picture it as an airport security lane. You show a boarding pass, your bag gets a tag, it goes through the X-ray against a checklist of red flags, and you get a green, amber, or red light. That is exactly what a fraud engine does to every payment.

✈️
The scenario we will trace

Someone taps a card for R12,500 on an account that is only 12 days old. In the few milliseconds before the bank says "hold on — let a human look at this," here is the exact journey that payment takes.

📥
Goes IN

A small bundle of facts about one payment, written as JSON (amount, account, country, account age...).

📤
Comes OUT

A verdict — ALLOW / REVIEW / BLOCK — plus a 0-to-1 risk score and a human-readable reason.

Here is the friendly role name to real code-name mapping you will reuse for the rest of the course:

TransactionController "Front Desk" — receives the request and sends back the reply.
JWT + Validation "Bouncer" — checks your pass and that your form is filled in correctly.
Idempotency "Memory" — remembers requests it has already answered.
IngestService "The Brain" — coordinates everything and records what happened.
Rule Engine "The Judge" — runs the red-flag checklist and decides the verdict.
Database "Filing Cabinet" — stores the event and the verdict permanently.

The form every payment must fill in

Before the engine will look at a payment, the payment has to match a strict template — like a customs form where every box is mandatory and checked. In the code this template is a record called TransactionRequest.

CODE 
public record TransactionRequest(
        @NotNull UUID txId,
        @NotBlank String accountId,
        @NotNull @DecimalMin(value = "0.0", inclusive = true)
        @Digits(integer = 15, fraction = 4) BigDecimal amount,
        @NotBlank @Pattern(regexp = "[A-Z]{3}", message = "currency must be ISO-4217 uppercase, e.g. ZAR") String currency,
        @NotBlank @Pattern(regexp = "[0-9]{4}", message = "mcc must be 4 numeric digits") String mcc,
        @NotBlank @Pattern(regexp = "WEB|MOBILE|POS|ATM|API") String channel,
        @NotBlank @Pattern(regexp = "[A-Z]{2}", message = "country must be ISO-3166-1 alpha-2 uppercase") String country,
        @NotBlank @Pattern(regexp = "[A-Z]{2}", message = "ipCountry must be ISO-3166-1 alpha-2 uppercase") String ipCountry,
        String deviceId,
        String merchantId,
        @NotNull @Min(0) Integer accountAgeDays,

PLAIN ENGLISH

This is the precise template every payment must match.

Every line needs a unique id and an account it belongs to.

The amount can never be negative — it must be zero or more.

Currency must be three capital letters like ZAR; the channel must be one of WEB, MOBILE, POS, ATM, or API.

Country codes must be two capital letters; account age must be zero or higher.

The @-labels are guardrails. Break any one of them and the request is rejected before any fraud check even runs.

Those @-labels are doing validation. They are the airport's "is your boarding pass even real?" check, done at the very front door.

In through the door, out with a verdict

The Front Desk (TransactionController) is where the payment enters the building. Once the checks pass, it hands the payment to The Brain and waits for the answer.

Hand the payment to The Brain (ingestService) and wait for a Decision — the verdict.

Turn that internal decision into the tidy reply the client will receive.

If the caller sent a do-not-repeat ticket (an Idempotency-Key)...

...file the answer under that ticket so a repeat request gets the same answer for free.

Reply with HTTP 202 ACCEPTED and the verdict.

🔢
202 is success, not a bug

An HTTP status code of 202 ACCEPTED is the engine's intended way of saying "got it, here is your verdict." If you expected a 200 and saw a 202, nothing is broken.

Why a retry never charges you twice

Networks drop. Apps time out and retry. So how does the engine avoid screening the same bag twice? With a one-time baggage tag: the Idempotency-Key.

CODE 
        if (idempotencyKey != null && !idempotencyKey.isBlank()) {
            var cached = idempotency.lookup(subject, idempotencyKey);
            if (cached.isPresent()) {
                if (!cached.get().bodyHash().equals(bodyHash)) {
                    ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.CONFLICT);
                    pd.setType(URI.create("https://fraud-engine.example/problems/idempotency-conflict"));
                    pd.setTitle("Idempotency-Key reused with different body");
                    pd.setDetail("The same Idempotency-Key was previously used with a different payload.");
                    pd.setProperty("idempotencyKey", idempotencyKey);
                    return ResponseEntity.status(HttpStatus.CONFLICT).body(pd);
                }
                // Same key + same body → return cached response verbatim.
                return ResponseEntity.status(HttpStatus.ACCEPTED).body(cached.get().response());
PLAIN ENGLISH

If the caller sent a do-not-repeat ticket, look it up before doing any real work.

If we have seen this ticket before, compare what was sent then versus now.

Same ticket but a different payment? That is suspicious bookkeeping — refuse with a 409 Conflict and explain why.

Same ticket and same payment? Just hand back the answer we already saved — no double processing.

The comparison uses a hash of the payload — a quick fingerprint — to tell "same payment" from "different payment."

💡
Key Insight

A retry should never cost you twice. Real systems hand out a one-time ticket so a repeated request returns the same answer instead of doing the work again. Engineers call this property idempotency.

Three habits of a trustworthy engine

Three design choices on this journey are worth naming, because you will see them in almost every serious backend you ever touch.

🎫

Idempotency-Key

A do-not-charge-twice ticket. The same ticket plus the same payment always returns the same saved answer — retries are safe.

🔒

One all-or-nothing write

The raw event and the verdict are saved together in a single database transaction — either both land or neither does. No half-saved records.

📋

Consistent error reports

When something is rejected, you get a structured explanation (RFC 7807 Problem Details) with a correlation id — not a cryptic crash.

Why you should care: knowing the request-to-response shape and where each stop lives is what lets you read an API, debug "my call returns something weird," and tell an AI assistant exactly where in the pipeline a change belongs.
