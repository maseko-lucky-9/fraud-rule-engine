Attack Your Own Engine

A second program whose entire job is to break the one you built — and turn every hole it finds into a new rule.

The Uncomfortable Question

You built a fraud engine. Here is the question every real team must ask: what does it miss? This module is a second program — written in Python — whose whole job is to attack your engine with real fraud tricks and write up every hole it finds.

💉
Think of it like a vaccine lab

You deliberately inject weakened versions of known attacks into the body (the engine), watch which ones the immune system fails to neutralize, and from each failure you design a new antibody — a draft rule that joins the body's defenses. Controlled exposure is what makes the system stronger.

🟢
Honest customers

Mostly the crowd: well-behaved accounts that form the clean baseline the attacks are measured against.

🎭
Scripted adversaries

Hand-written evasion tricks — known fraud patterns engineered to dodge specific rules.

🤖
LLM-invented adversaries

A local AI invents fresh attacks the humans did not think of — used non-authoritatively, exactly like Module 5 taught.

This whole setup is a red team / penetration test built as a simulator / harness — and it hits the live engine over its real network door.

Two Tricks That Walk Right Past the Alarms

Each scripted attack is built to dodge one specific rule. The first spreads a flood of tiny charges across many accounts so no single account looks busy.

CODE 
def build_card_testing(*, seed: int) -> FraudScenario:
    """Distributed micro-tx across 20 accounts — evades per-account VELOCITY_BURST."""
    sid = "evasion_card_testing"
    base = base_time(hour_sast=14)
    steps: list[ScenarioStep] = []
    for acc_n in range(20):
        for tx_n in range(10):  # 10 per account × 20 accounts = 200 micro-tx
            steps.append(
                ScenarioStep(
                    tx=benign_tx(
                        scenario_id=sid, step=len(steps), seed=seed,
                        account_id=f"ACC-EV-CT-{acc_n:02d}",
                        amount=Decimal("0.99"),
                        timestamp=base + minutes(tx_n),
                        device_id=f"dev-CT-{acc_n:02d}",
                        merchant_id="MERCH-OK-WEB-001",
                    ),
                )
            )
PLAIN ENGLISH

A criminal with a batch of stolen card numbers wants to know which still work.

So they run a flood of tiny $0.99 charges — that is "card-testing."

The engine's speed alarm only counts how fast ONE account spends.

So this attack spreads 200 charges across 20 different accounts — each one looks calm.

This code builds exactly that crowd to prove the alarm never goes off.

This trick is called card-testing, and it dodges the engine's per-account speed rule. The second trick stays just under the big-amount line, over and over.

def build_structuring(*, seed: int) -> FraudScenario:
    """Single account: $9,999 every 90 min — slips under HIGH_AMOUNT cutoff."""
    sid = "evasion_structuring"
    base = base_time(hour_sast=10)
    steps = tuple(
        ScenarioStep(
            tx=benign_tx(
                scenario_id=sid, step=i, seed=seed,
                account_id="ACC-EV-STR-1",
                amount=Decimal("9999.00"),
                timestamp=base + hours(i * 90 // 60) + minutes(i * 90 % 60),
                account_age_days=15,  # younger account intensifies the miss
                merchant_id="MERCH-OK-001",
            ),
        )
        for i in range(8)
    )
    return FraudScenario(
        id=sid, archetype="structuring", targets_rule="HIGH_AMOUNT_NEW_ACCOUNT",
        expected_outcome="miss",
        description=(
            "$9,999 transactions every 90 minutes on a 15-day-old account. "
            "HIGH_AMOUNT_NEW_ACCOUNT triggers at >$10,000 — each transaction "
            "is sub-threshold. AML structuring/smurfing pattern."
        ),
PLAIN ENGLISH

The big-amount rule only fires above $10,000.

So the attacker sends $9,999 over and over — always one dollar under the line.

Each payment looks innocent; together they move a fortune.

This is the money-laundering trick called "structuring."

It is tagged expected_outcome="miss" — today's engine cannot add up many payments over time.

🩺
Key Insight: a "miss" here is a passing test

A miss documents a real, known gap honestly — so the team can decide to close it, not pretend it isn't there. Naming your weaknesses is how you fix them.

This second trick is structuring / smurfing (AML) — and another known family, account takeover (ATO), is tested the same way.

The Clean Baseline: Honest Customers

You cannot judge an attack without something normal to compare it to. The honest persona / agent is engineered to stay under every alarm. If the engine ever flags one, you know something broke.

🎲
Same seed → same crowd

The crowd is generated from a seed / deterministic value, so the exact same accounts and attacks appear every run. Tests that produce different results each time are useless — repeatability is what makes them trustworthy.

The Scoreboard: Catches vs. Misses

After the crowd hits the live engine, an analysis step in pandas / DataFrame tallies, for every test, what the engine should have done versus what it actually did.

CODE 
    for _, row in df.iterrows():
        classification = _scenario_classification(row.get("scenario_id") or "")
        if classification is None:
            continue
        rule, kind = classification
        matched = rule in row["matched_rules_list"]
        bucket = rows.setdefault(rule, {"tp": 0, "fp": 0, "fn": 0, "tn": 0})
        if kind == "positive" and matched:
            bucket["tp"] += 1
        elif kind == "positive" and not matched:
            bucket["fn"] += 1
        elif kind in {"negative", "boundary"} and not matched:
            bucket["tn"] += 1
        elif kind in {"negative", "boundary"} and matched:
            bucket["fp"] += 1
PLAIN ENGLISH

For every test, the code already knows what the engine SHOULD have done.

Should-catch and did → "true positive" (a good catch).

Should-catch but didn't → "false negative" — a dangerous miss.

A clean customer wrongly flagged → "false positive."

These four tallies per rule become the engine's report card.

Those four tallies turn into two famous numbers. A false positive / false negative count feeds precision / recall — the engine's report card.

🔒
Numbers from code, prose from the AI

Every authoritative number is computed deterministically by this code. The AI only writes the narrative and never sees the raw rows — so it cannot invent or contradict a statistic. (This is Module 5's "AI advises, never decides," applied to reporting.)

Closing the Loop: A Miss Becomes a New Rule

This is the payoff. The feedback loop closes when the auditor turns every genuine miss into a proposed new rule.

CODE 
def _default_findings_from_evasion(metrics: RunMetrics) -> list[FindingDraft]:
    drafts: list[FindingDraft] = []
    for outcome in metrics.evasion_outcomes:
        sid = outcome["scenario_id"]
        if outcome.get("actual") != "miss":
            continue
        if sid not in _DEFAULT_STUBS:
            continue
        severity, title, stub = _DEFAULT_STUBS[sid]
        drafts.append(FindingDraft(
            severity=severity, scenario_id=sid, title=title,
            proposed_yaml_stub=stub,
        ))
    drafts.sort(key=lambda d: (d.severity, d.scenario_id))
    return drafts
PLAIN ENGLISH

The auditor looks at every attack.

Whenever the engine actually MISSED one...

...it pulls a matching draft rule off the shelf.

It adds it to the report as a ranked finding (P0 most urgent down to P2).

A hole found by attacking becomes a proposed new rule — the same kind the engine hot-reloads in Module 3.

But the auditor must never propose a rule the engine cannot run. A predicate allowlist check walks the draft and downgrades anything that uses an unknown building block.

Before a draft is called "drop-in ready," walk every condition in it.

A block the engine recognizes (an amount or country check) is fine.

So the report never ships a rule that would crash the engine.

You Now Understand How a Fraud Engine Thinks

You made it. You can now trace a payment from the moment it arrives all the way to a decision — and back again as a brand-new rule. Here is the whole course in one breath:

1
The transaction arrives

A single payment lands at the engine's network door, carrying everything the rules need to judge it.

2
The engine inspects it

It checks the payment against each rule, looking for danger signs without trusting any single one blindly.

3
Rules are data, not code

The rules live in editable YAML files the engine hot-reloads — so you change behaviour without touching the program.

4
Scores add up to a verdict

Each matched rule contributes a weight; the totals decide allow, review, or block.

5
The AI consultant advises

A local AI explains and suggests — but the deterministic rules, never the AI, make the final call.

6
You attack your own engine

A red-team simulator finds the holes, and each hole becomes a new rule hot-reloaded back into Module 3.

🏆
The two lessons to carry with you

Rules as data (Module 3): keep the changeable parts in editable files so you can adapt without rewriting the program. AI advises, never decides (Module 5): let the AI explain and suggest, but keep the final, accountable decision in deterministic code. Build with both instincts and you will ship software you can actually trust.

And the most valuable instinct of all: assume your thing has holes, then go find them on purpose. That is how weaknesses become strengths — and how you escape the AI bug-loop to ship something reliable.
