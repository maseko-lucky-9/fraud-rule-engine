The Journey of a Transaction

From a tap on a card to a verdict in milliseconds — the exact path your payment takes through a fraud engine.

What is this thing?

This whole course is about one program: a real-time brain that scores bank card payments and instantly says ALLOW, REVIEW, or BLOCK — always with a plain-English reason attached.

Picture it as an airport security lane. You show a boarding pass, your bag gets a tag, it goes through the X-ray against a checklist of red flags, and you get a green, amber, or red light. That is exactly what a fraud engine does to every payment.

The form every payment must fill in

Before the engine will look at a payment, the payment has to match a strict template — like a customs form where every box is mandatory and checked. In the code this template is a record called TransactionRequest.

PLAIN ENGLISH

This is the precise template every payment must match.

Every line needs a unique id and an account it belongs to.

The amount can never be negative — it must be zero or more.

Currency must be three capital letters like ZAR; the channel must be one of WEB, MOBILE, POS, ATM, or API.

Country codes must be two capital letters; account age must be zero or higher.

The @-labels are guardrails. Break any one of them and the request is rejected before any fraud check even runs.

Those @-labels are doing validation. They are the airport's "is your boarding pass even real?" check, done at the very front door.

Why a retry never charges you twice

Networks drop. Apps time out and retry. So how does the engine avoid screening the same bag twice? With a one-time baggage tag: the Idempotency-Key.

CODE 
        if (idempotencyKey != null && !idempotencyKey.isBlank()) {
            var cached = idempotency.lookup(subject, idempotencyKey);
            if (cached.isPresent()) {
                if (!cached.get().bodyHash().equals(bodyHash)) {
                    ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.CONFLICT);
                    pd.setType(URI.create("https://fraud-engine.example/problems/idempotency-conflict"));
                    pd.setTitle("Idempotency-Key reused with different body");
                    pd.setDetail("The same Idempotency-Key was previously used with a different payload.");
                    pd.setProperty("idempotencyKey", idempotencyKey);
                    return ResponseEntity.status(HttpStatus.CONFLICT).body(pd);
                }
                // Same key + same body → return cached response verbatim.
                return ResponseEntity.status(HttpStatus.ACCEPTED).body(cached.get().response());
PLAIN ENGLISH

If the caller sent a do-not-repeat ticket, look it up before doing any real work.

If we have seen this ticket before, compare what was sent then versus now.

Same ticket but a different payment? That is suspicious bookkeeping — refuse with a 409 Conflict and explain why.

Same ticket and same payment? Just hand back the answer we already saved — no double processing.

The comparison uses a hash of the payload — a quick fingerprint — to tell "same payment" from "different payment."

💡
Key Insight

A retry should never cost you twice. Real systems hand out a one-time ticket so a repeated request returns the same answer instead of doing the work again. Engineers call this property idempotency.

Three habits of a trustworthy engine

Three design choices on this journey are worth naming, because you will see them in almost every serious backend you ever touch.

🎫

Idempotency-Key

A do-not-charge-twice ticket. The same ticket plus the same payment always returns the same saved answer — retries are safe.

🔒

One all-or-nothing write

The raw event and the verdict are saved together in a single database transaction — either both land or neither does. No half-saved records.

📋

Consistent error reports

When something is rejected, you get a structured explanation (RFC 7807 Problem Details) with a correlation id — not a cryptic crash.

Why you should care: knowing the request-to-response shape and where each stop lives is what lets you read an API, debug "my call returns something weird," and tell an AI assistant exactly where in the pipeline a change belongs.

The shared vocabulary

Every department needs to agree on what a payment is and what a verdict is. That agreement lives in the domain model: simple, plain-data definitions with no machinery bolted on.

CODE

PLAIN ENGLISH

A Transaction is just the facts about one card payment.

It has an id, the account, and the amount and currency.

It records where it happened — the country versus the country the internet connection came from.

Plus the device, the merchant, how old the account is, and the time.

It even lists the ways a payment can arrive: web, mobile, card machine, ATM, or another program.

Plain data, nothing technical bolted on — so its business meaning stays obvious.

This shape is a record — a tidy container for facts. The enum at the bottom is a fixed menu: a payment can only ever arrive one of those five ways.

    public Decision {

PLAIN ENGLISH

A Decision is the verdict and the full story behind it.

It says which transaction, the status, and a 0-to-1 score of how risky it looked.

It records which version of the rulebook was used.

And the exact list of rules that fired, plus when it was evaluated.

It refuses to even exist if the score is a nonsense number.

It copies the matched-rules list so nobody can secretly rewrite the explanation later.

This is the record a regulator relies on.

And the verdict itself is one of exactly three words — an enum again. When several rules fire, the strictest wins: BLOCK beats REVIEW beats APPROVE.

    APPROVE,
    REVIEW,
    BLOCK

PLAIN ENGLISH

Every transaction ends as exactly one of three verdicts.

Let it through, or pause it for a human, or stop it dead.

There is no fourth option — nothing falls through the cracks.

Notice the Transaction holds an account id and a device id, not a person’s name. Keeping PII out of the core data is deliberate: less sensitive information flowing around means less that can leak.

All these departments could have been built as separate mini-programs that phone each other over the network. Instead they share one building. Why?

The whole system has a single “on” switch. One method boots every department at once — that is what makes it a monolith.

PLAIN ENGLISH

That single starting point is exactly what makes this a monolith — one program, not many separate services.

The trick is that the walls between departments are still real — they are just enforced inside one app. Engineers call this a modular monolith. Here is the trade-off the team weighed in their decision record (ADR-0002):

🏢

Modular Monolith

✅ One app, one deploy
✅ One all-or-nothing save — verdict and reasons land together or not at all
✅ One clean audit trail
✅ Walls enforced inside, with the option to split later

🌏

Microservices

⚠️ Many separate services to run and watch
⚠️ Network calls between them — slower, can fail mid-flight
⚠️ Eventual consistency — parts can briefly disagree
⚠️ Much harder to keep one clean audit trail

A bank wants one thing to microservices can offer scale, but a fraud bank wanted correctness and compliance first — so it chose one program now, with clean walls so it can split later if it ever needs to.

03

The Rulebook

How the engine decides — and why its rules live in a file an analyst can edit, not in code.

The rule was never hiding in the code

Back in Module 1, a rule called HIGH_AMOUNT_NEW_ACCOUNT decided to flag that R12,500 payment for human review. Here is the surprise: that rule is not buried inside the program.

It lives in a plain text file a fraud analyst can open and edit — and change without a single developer or redeploy.

🎧
Think of a Smart Playlist

In a music app you build a smart playlist from a settings panel: "if genre is Jazz AND year is after 2000, add it." You pick conditions from a fixed dropdown, hit apply, and the playlist updates live — no coding. A fraud rulebook works exactly the same way: the rules are the playlist settings, the available tests are the dropdown, and hot-reload is hitting apply.

📝
The rules = the playlist settings

Editable data: thresholds, conditions, and what to do when they match.

☰
The predicates = the dropdown of conditions

A fixed menu of building-block tests an analyst chooses from.

⚡
Hot reload = hitting apply

The new rulebook takes effect live, without restarting the app.

A whole rule, written as settings

Here is the actual HIGH_AMOUNT_NEW_ACCOUNT rule. It is written in YAML, a settings format made to be human-readable. Read the right side first.

CODE · rule-set-v1.yml 
    - id: HIGH_AMOUNT_NEW_ACCOUNT
      priority: 800
      severity: HIGH
      shortCircuit: false
      condition:
        all:
          - predicate: amountAbove
            args: { value: 10000, currency: "ZAR" }
          - predicate: accountAgeBelow
            args: { days: 30 }
      action:
        flag: REVIEW
        score: 0.85
        reason: "High amount on a young account."
PLAIN ENGLISH

This rule has a name (an id) so people and logs can refer to it.

Priority 800 sets how early it runs — higher numbers run first.

Severity HIGH labels how dangerous a match is, for reporting.

shortCircuit false means: if this matches, keep checking other rules too.

Now the condition — the IF part of the rule.

all means every test below must pass (this is AND).

Test 1: use the amountAbove check...

...with these settings: amount over 10,000 in rand (ZAR).

Test 2: use the accountAgeBelow check...

...with this setting: account younger than 30 days.

If both pass, here is what to do (the action):

Flag it REVIEW — send it to a human, do not auto-block.

Attach a risk score of 0.85 (out of 1.0).

And a readable reason analysts will actually see.

No programming anywhere. An analyst can change 10000 to 8000, save, reload — and the threshold is now lower. No developer needed.

One test, reused everywhere

The YAML said amountAbove. That name points to a small piece of real code — a predicate. It is written once and reused for every amount rule.

CODE · AmountAbovePredicate.java 
    @Override
    public boolean test(PredicateContext ctx, Map<String, Object> args) {
        BigDecimal threshold = PredicateArgs.requireBigDecimal(args, "value");
        String currency = PredicateArgs.requireString(args, "currency");
        var tx = ctx.transaction();
        return currency.equals(tx.currency()) && tx.amount().compareTo(threshold) > 0;
    }
PLAIN ENGLISH

This is the one reusable fraud test, named amountAbove.

It runs a yes/no check, given the transaction and the rule's settings.

Read the threshold number out of the settings (the "value").

Read the currency out of the settings too.

Grab the transaction we are checking.

Return true only if the currency matches AND the amount is bigger than the threshold.

Done — one clean yes/no answer.

💡
Key Insight: rules are data, not code

The same code serves a 10,000 rule and a 5,000 rule — the number comes from the YAML, not the code. When you separate the rules from the machinery, the people who understand fraud can change the rules, and the people who build software can improve the machinery — independently. Ask your AI assistant for this whenever thresholds might change: "don't hardcode these values; make them configurable data I can change without redeploying."

How does the name find the code?

At startup the app builds a phone book — a registry — filing every test under its name. If two tests claim the same name, it refuses to start.

CODE · PredicateRegistry.java 
    public PredicateRegistry(List<Predicate> predicates) {
        Map<String, Predicate> map = new HashMap<>();
        for (Predicate p : predicates) {
            Predicate existing = map.putIfAbsent(p.id(), p);
            if (existing != null) {
                throw new IllegalStateException("Duplicate predicate id: " + p.id()
                        + " (" + existing.getClass().getName() + " vs " + p.getClass().getName() + ")");
            }
        }
        this.byId = Map.copyOf(map);
    }
PLAIN ENGLISH

At startup, collect every fraud test that exists.

Make an empty lookup table to file them in.

Go through the tests one by one.

File each one under its name — but check if that name is already taken.

If two tests claim the same name...

...refuse to start, and say exactly which two clashed.

(So you are never left guessing which one silently won.)

Otherwise, lock the finished phone book in place.

The beating heart: walking the rules

Now the engine has a transaction and a rulebook. It walks the rules one at a time, in priority order, keeping the strictest verdict it has seen.

CODE · RuleEngine.java 
            for (Rule rule : snapshot.rules()) {
                if (evaluateCondition(rule.condition(), ctx)) {
                    Action action = rule.action();
                    matched.add(new RuleResult(rule.id(), rule.priority(), action.reason()));
                    maxScore = Math.max(maxScore, action.score());
                    status = stricter(status, action.flag());
                    if (rule.shortCircuit()) break;
                }
            }
PLAIN ENGLISH

Go through every rule in the rulebook, in order.

For each rule, check: is its condition true for this transaction?

If yes, grab what the rule wants to do (its action).

Record the match — rule name, priority, and reason — for the audit trail.

Keep the highest risk score seen so far (not a total — the max).

Upgrade to the strictest verdict so far (REVIEW can become BLOCK, never the reverse).

If this rule says shortCircuit, stop right now — the answer is final.

Otherwise, keep walking the rest of the rules.

Strictest verdict, highest score

Most-serious checks run first, and an obvious BLOCK can short-circuit the rest. The final verdict is the strictest rule that matched — and the score is the highest match, never a sum. Two REVIEWs do not add up to a BLOCK.

Joining tests — and swapping the rulebook live

A condition can be a single test, or a group joined by all (AND) or any (OR). Groups can nest, so analysts build rich logic in plain YAML.

CODE · RuleEngine.java 
    private boolean evaluateCondition(Condition cond, PredicateContext ctx) {
        return switch (cond) {
            case Condition.Atomic atomic -> registry.require(atomic.predicateId()).test(ctx, atomic.args());
            case Condition.All all -> {
                for (Condition c : all.children()) {
                    if (!evaluateCondition(c, ctx)) yield false;
                }
                yield true;
            }
            case Condition.Any any -> {
                for (Condition c : any.children()) {
                    if (evaluateCondition(c, ctx)) yield true;
                }
                yield false;
            }
        };
    }
PLAIN ENGLISH

Decide whether one condition is true for this transaction.

Look at what kind of condition it is.

If it is a single test, look it up by name and run it.

If it is an "all" group (AND)...

...check each test inside it...

...and the moment one fails, the whole group is false (stop early).

If they all passed, the group is true.

If it is an "any" group (OR)...

...check each test inside it...

...and the moment one passes, the whole group is true (stop early).

If none passed, the group is false.

The hot-reload button

When an analyst changes a threshold, an operator hits a web button. The app re-reads the YAML and, if it is valid, swaps it in live. A broken file is rejected and the old rulebook keeps running.

CODE · AdminController.java 
    public ResponseEntity<?> reload() {
        try {
            RuleSet rs = loader.load(resourceLoader.getResource(rulesPath));
            int oldVersion = engine.active() == null ? -1 : engine.active().version();
            engine.install(rs);
            log.info("Reload OK: {} → {} (rules: {})", oldVersion, rs.version(), rs.rules().size());
            return ResponseEntity.ok(Map.of(
                    "previousVersion", oldVersion,
                    "currentVersion", rs.version(),
                    "ruleCount", rs.rules().size()
            ));
        } catch (RuleValidationException e) {
            reloadFailedCounter.increment();
            log.error("Reload REJECTED: {}", e.getMessage());
            ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, e.getMessage());
            pd.setProperty("errors", e.errors());
            pd.setProperty("activeVersion", engine.active() == null ? null : engine.active().version());
            return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY).body(pd);
        }
    }
PLAIN ENGLISH

An operator hits this web button to reload the rules.

Try to do it — but be ready to catch a problem.

Re-read the YAML rules file from disk.

Note which version is currently live, so we can report the change.

Swap the new rulebook in as the live one.

Log a friendly "Reload OK: old → new" with the rule count.

Report back the old version, new version, and how many rules.

But if the new file fails validation...

...count the failure, and log "Reload REJECTED" with why.

Build a clear error — 422 Unprocessable Entity — with the message.

Attach the exact list of problems found.

And note which version is still safely live (the old one).

Send the 422 back. Fraud detection was never switched off.

Four ideas that make this safe

Everything you just saw rests on four design choices. These are the patterns to ask your AI assistant for whenever behaviour might change.

📝

Rules as data, not code

The rules live in a versioned YAML file. Business experts change behaviour; engineers improve the machinery — independently.

📖

A vocabulary of tests

The registry is a fixed menu of reusable predicates. Rules pick from it by name — the same test powers many rules.

⚡

Atomic hot-swap

Apply a new rulebook live, no restart. The engine always runs one complete rulebook — never a half-applied mix.

🛡

Validate before install

A broken file is rejected with a 422 and a list of problems. The old, working rulebook keeps running. Typos never disable detection.

Never Lose a Decision

The hard part nobody sees: making sure a fraud decision is never made twice, never silently lost, and that a card-tester is actually counted in time.

The engine has decided. Now the real work begins.

Picking approve or review is the easy part. The hard part is the plumbing around it: a retried payment must not be charged twice, the "decision announced" message must never vanish, and a burst of six payments in one second must actually be counted.

Think of a meticulous bank back office that never loses a slip. Three little rituals keep it honest.

🎫
The coat-check ticket

Idempotency: hand over the same ticket twice, get the same coat back. Never a second coat.

⏱️
The fading hand-stamp

The nightclub counter scrubs off stamps older than 60 seconds, then counts the rest in one glance — deciding if a card has come and gone too many times.

📧
The certified-mail shelf

Instead of risking the message not being heard, the clerk spikes a paper slip on an outbound shelf in the same motion as recording the decision. A runner delivers every slip later.

Ritual 1 — The do-not-repeat ticket

When your phone retries a payment on a flaky connection, the bank could easily process it twice. To stop that, every request carries an Idempotency-Key — a coat-check ticket. Two small tricks make the ticket trustworthy.

CODE 
    public static String hashBody(byte[] body) {
        try {
            MessageDigest md = MessageDigest.getInstance("SHA-256");
            byte[] digest = md.digest(body);
            StringBuilder sb = new StringBuilder(digest.length * 2);
            for (byte b : digest) sb.append(String.format("%02x", b));
            return sb.toString();
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException("SHA-256 unavailable", e);
        }
    }

    public static byte[] toBytes(String s) {
        return s == null ? new byte[0] : s.getBytes(StandardCharsets.UTF_8);
    }

    private static String redisKey(String subject, String key) {
        return "idem:" + (subject == null ? "anon" : subject) + ":" + key;
    }
PLAIN ENGLISH

Two safety tricks live here.

hashBody turns the whole request into a short, unique fingerprint using SHA-256.

So the engine can check that a reused ticket really carries the same content — not a sneaky different payment under an old ticket.

redisKey glues the customer's identity (the subject) onto the ticket.

That means one customer can never reuse another customer's ticket to read or hijack their result. The ticket is tied to you.

💭
Why glue identity to the key?

A coat-check ticket only works because it is tied to your coat. Without the customer prefix, a guessed ticket number could fetch someone else's fraud result.

Ritual 2 — Counting that fades on its own

To catch a card-tester, the engine asks "how many payments from this account in the last 60 seconds?" The simplest version, for a single machine, keeps a time-ordered list and drops anything too old.

CODE 
    @Override
    public int recordAndCountWithin(String accountId, String txId, Instant at, Duration window) {
        long now = at.toEpochMilli();
        long floor = now - window.toMillis();
        Deque<Long> deque = velocityByAccount.computeIfAbsent(accountId, k -> new ArrayDeque<>());
        synchronized (deque) {
            // Evict entries older than or equal to floor.
            Iterator<Long> it = deque.iterator();
            while (it.hasNext()) {
                if (it.next() <= floor) {
                    it.remove();
                } else {
                    break; // deque is ordered by arrival ≈ timestamp asc
                }
            }
            deque.addLast(now);
            return deque.size();
        }
PLAIN ENGLISH

The single-machine way to count recent transactions for one account.

Work out the cut-off line: "now" minus the window (say, 60 seconds ago).

Walk the list of timestamps and throw away every stamp older than the cut-off.

Add the current transaction's time to the end, then return how many remain.

The synchronized lock stops two requests for the same account from tripping over each other — a guard against a race condition.

⏱️
Like a nightclub hand-stamp

Old stamps fade and get scrubbed off; the bouncer counts only what is still glowing. The window is the fade time.

Counting correctly when there are many machines

One machine is easy. But a real bank runs many copies of the engine at once, so the count must live in a shared place: Redis. The trick is a tiny script that Redis runs atomically — start to finish — before anything else touches that account.

CODE 
local key      = KEYS[1]
local now_ms   = tonumber(ARGV[1])
local floor_ms = tonumber(ARGV[2])
local member   = ARGV[3]
local ttl_sec  = tonumber(ARGV[4])

-- Evict entries strictly older than the window floor.
redis.call('ZREMRANGEBYSCORE', key, '-inf', floor_ms - 1)

-- Add the new entry. Score = now_ms, member = txId.
redis.call('ZADD', key, now_ms, member)

-- Refresh the per-account TTL so the key dies if the account goes silent.
redis.call('EXPIRE', key, ttl_sec)

return tonumber(redis.call('ZCARD', key))
PLAIN ENGLISH

This little Lua script runs inside Redis and does four things in one breath.

Remove every event older than the window floor.

Add the new event, stamped with its time.

Refresh the auto-delete timer so the count vanishes if the account goes quiet.

Return the new count.

Because Redis finishes the whole script before any other command touches that account, two transactions in the same millisecond can never miscount each other.

Spot the bug: a counter that lets bursts slip through

Here is a tempting "simpler" velocity counter that stores timestamps in a Set. It looks fine, but a card-tester firing fast payments would walk right past the limit. Click the line that causes it.

Find the flaw in this velocity counter:

1 long now = at.toEpochMilli();
2 long floor = now - window.toMillis();
3 Set<Long> stamps = byAccount.computeIfAbsent(accountId, k -> new HashSet<>());
4 stamps.removeIf(ts -> ts <= floor);
5 stamps.add(now);
6 return stamps.size();
🚨
Why this matters

A Set stores only one copy of each value. Two payments landing in the same millisecond share a timestamp, so the Set collapses them into one. A fast burst gets undercounted and slips past the limit — which is exactly why the real code uses a Deque that keeps every entry.

Ritual 3 — The certified-mail shelf (the outbox)

Now the decision must be both saved and announced to other systems over a message bus. Doing those as two separate steps is a classic trap.

💡
Key Insight: the dual-write problem

Saving to a database AND sending a message are two separate actions — one can succeed while the other fails, losing or duplicating events. The fix: make the intent to send part of the same save, and deliver it afterward.

The transactional outbox solves the dual-write problem. Walk the journey of one decision below.

Inside the runner: the drain loop

The poller is the runner who carries slips from the shelf to the mailroom. Every half-second it grabs a batch and fires them all at once.

CODE 
    @Scheduled(fixedDelayString = "${app.outbox.poll-interval-ms:500}")
    @Transactional
    public void drain() {
        List<OutboxEntity> batch = outboxRepo.findPendingForUpdate(batchSize);
        if (batch.isEmpty()) {
            return;
        }
        log.debug("outbox: draining {} pending rows (lock held until commit)", batch.size());

        // Dispatch every send in parallel so a single slow row can't stall the batch.
        Map<OutboxEntity, CompletableFuture<?>> inflight = new HashMap<>(batch.size());
        Map<OutboxEntity, String> lastErrors = new HashMap<>();
        for (OutboxEntity row : batch) {
            CompletableFuture<?> future = kafkaTemplate
                    .send(KafkaTopics.DECISIONS_OUT, row.getAggregateId().toString(), row.getPayload())
                    .toCompletableFuture();
            inflight.put(row, future);
        }

        CompletableFuture<Void> all = CompletableFuture.allOf(inflight.values().toArray(new CompletableFuture[0]));
        try {
            all.get(publishTimeoutMs, TimeUnit.MILLISECONDS);
        } catch (InterruptedException ie) {
            Thread.currentThread().interrupt();
        } catch (ExecutionException | TimeoutException ex) {
            log.warn("outbox: batch publish wait failed — settling per-row. cause={}", ex.toString());
        }
PLAIN ENGLISH

Every half-second this background job wakes up.

It grabs a batch of unsent "to-publish" notes from the database. If there are none, it goes back to sleep.

It fires them all at the message bus at once — in parallel, so one slow message cannot hold up the rest.

Then it waits, but only up to a time limit.

If Kafka is slow or down, the wait gives up cleanly instead of hanging forever — and it will decide what to do with each note individually.

Settling each slip: done, retry, or dead-letter

After the send attempt, the runner inspects each note one by one. Three fates: delivered, try again later, or give up and file it away.

CODE 
        for (Map.Entry<OutboxEntity, CompletableFuture<?>> e : inflight.entrySet()) {
            OutboxEntity row = e.getKey();
            CompletableFuture<?> f = e.getValue();
            if (f.isDone() && !f.isCompletedExceptionally()) {
                row.markProcessed();

PLAIN ENGLISH

Look at each note's send result, one at a time.

Delivered? Stamp it "processed" so it is never sent again.

Failed? Add one to its retry count and leave it for next time.

Unless it has failed too many times (default 10)...

...then move it to a dead-letter drawer so one hopeless note does not clog the live queue forever.

The four reliability moves, on cards

These four patterns recur across almost every serious system. Recognising them lets you ask an AI for the right design instead of the buggy two-step.

🎫

Idempotency

The do-not-repeat ticket. A retried request is recognised and answered once — never charged twice.

📧

Transactional outbox

Saves the decision and a to-send note together, then delivers later. Solves the dual-write problem.

⚡

Atomic counting

A tiny Redis script counts recent events with no interruption, so concurrent writes never miscount.

☠️

Dead-letter drawer

A holding area for hopeless messages so they stop blocking everyone else. Failures get quarantined, not lost.

📧
At-least-once delivery

Because the outbox keeps retrying until a note is delivered, every event is guaranteed to arrive at least once — even if the broker was briefly down. Listeners are built to shrug off the occasional duplicate.

05

The AI Consultant — and Why It Is Never Allowed to Decide

How to bolt an AI assistant onto a system that blocks people's money — without ever letting the AI make that call.

The most important question in this whole codebase

Everyone wants to bolt AI onto everything. So here is the question that matters most: how do you add an AI assistant to a system that decides whether to block someone's money — without ever letting the AI make that call?

Think of a car's built-in GPS co-pilot. The GPS suggests a route. But it can never touch the steering wheel or the brakes — you always drive. Even when it says confidently "turn here," the dashboard still shows "driver must confirm." And if the GPS loses signal, the car keeps driving exactly as before.

🚗
The driver = the rule engine

The deterministic rule engine makes the real decision. It is the only thing with hands on the wheel.

📡
The GPS = the AI advisor

A local AI model writes a short note after the decision, only to help a human reviewer. Advice only, never control.

💡
Why you should care

This is the lesson for steering AI: keep the AI a helpful commentator, never the judge, in anything high-stakes. When you build with AI, you will learn to ask: where is the human in the loop, and what happens when the model is wrong or down?

First, a promise: "any advisor must keep this shape"

Before plugging in any AI, the code writes down a contract — an interface. It says: whoever the advisor is, it must answer one question and admit whether it is even real.

CODE 
public interface AdvisoryService {

    AdvisoryResponse adviseOn(Decision decision);

    /** Indicates whether a real advisor (e.g. Ollama) is wired up. */
    default boolean enabled() { return false; }
}
PLAIN ENGLISH

A promise that any AI advisor must keep.

One method: hand it a finished decision, get back commentary. That is its only job.

A second question: "are you a real advisor?"

The default answer is "no." Off by default — you have to actively switch a real one on.

🤝
Why the contract comes first

Because everything talks to this promise — not to "the AI" directly — the rest of the app never has to know whether AI is actually on. Swapping advisors becomes a one-line setting change. Engineers call this the strategy pattern.

One switch: AI OFF vs AI ON

There are two advisors that keep the same promise. A single setting — app.advisory.enabled — decides which one the app loads. Nothing else changes.

🔘

OFF (the default)

🔥

ON

Loads the real Ollama advisor. It calls a local model with a 2-second fuse, returns commentary — but still flags humanReviewRequired = true.

        drafts.append(FindingDraft(
            severity=severity, scenario_id=sid, title=title,
            proposed_yaml_stub=stub,
        ))
    drafts.sort(key=lambda d: (d.severity, d.scenario_id))
    return drafts

A red-team simulator finds the holes, and each hole becomes a new rule hot-reloaded back into Module 3.

The two lessons to carry with you

Rules as data (Module 3): keep the changeable parts in editable files so you can adapt without rewriting the program. AI advises, never decides (Module 5): let the AI explain and suggest, but keep the final, accountable decision in deterministic code. Build with both instincts and you will ship software you can actually trust.

And the most valuable instinct of all: assume your thing has holes, then go find them on purpose. That is how weaknesses become strengths — and how you escape the AI bug-loop to ship something reliable.
